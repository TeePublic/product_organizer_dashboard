# Refreshing the dashboard data

## Roadmap freeze (Jay, Nov 10): a refresh does not touch the Roadmap tab or Recent impact
The Roadmap tab is built from the sheet (next section), and Jay and Tom own everything else on it until they lift this freeze. A refresh, by hand or scheduled, must **not**:
- Edit `data/roadmap-coming-soon.js` or `data/sources.js` in any way. That means no projects, statuses, dates, links or text (`d`, `why`, `tags`), and nothing in `COMING.post`, `COMING.board`, `COMING.wins`, `COMING_PREV`, `COMING.asOf`, `ROADMAP_REVIEW`, `TEAM_MEETINGS`, `PEOPLE`, `DATES`, `VEL`, `HOURLY`, `RELN`, or their header comments.
- Edit the Roadmap or Recent impact code in `app.js`, `styles.css` or `index.html` (the Timeline and List views, sections, filters, pop-up, wins cards).
- Read Slack, Jira, Confluence, the calendar or meeting notes in order to change the roadmap or wins. Skip "Recent wins" and the "after each Executive Roadmap Review" steps below while the freeze is on.
- "Fix" a `npm run check` failure that is about those files (a missing source link, a dash on a win, a stale date). Do not edit around it. Stop before committing and tell Jay what failed.

Everything outside the roadmap (CVR pages, A/B tests, other tabs, the `PROD` dates and the rest of `data/`) is refreshed as before. If a roadmap change is needed, the Product Manager fixes the sheet, or Jay or Tom make the change on purpose. Do not work around the freeze.

The page is static: it shows whatever is in `data/` at deploy time. Updating it means changing those files and pushing to `master`.
There are two exceptions. On the Roadmap tab, each project's status, launch date and Jira link are patched at load from the latest snapshot of the sheet (see "The Roadmap tab comes from the sheet"). And the CVR numbers (CVR, sessions, the channel, device, funnel and region breakdowns, revenue, orders and payments) are refreshed from Amplitude by a Vercel job and applied at load from the latest snapshot (see "The CVR numbers come from Amplitude automatically").
Vercel redeploys automatically (about a minute). Shared features (ticks, topics, flags) live in the database and are not affected.
Mike pushes straight to `master`: there is no pull request or approval step. Jay and Tom push to `master` too, so every run (by hand or scheduled) must first bring in the latest `master` by rebasing, never by merging (see "Branch rules").

## The Roadmap tab is built from the sheet (Jay, Nov 10; supersedes the Nov 9 "sheet patches existing cards" rule)
The Active Work tab of the Product Org Dashboard sheet is the only source for the Roadmap tab, and **the sheet decides which cards exist**: every filled row becomes one card, in sheet order, under the team the row names. A row added to the sheet appears at the next pull; a row removed from the sheet disappears. Slack and Jira are not read for roadmap items. A Vercel job (`api/roadmap-refresh.js`) reads the tab twice a day (about 7:40 AM and 3:40 PM ET; the schedule is in UTC, so the ET times move an hour when daylight saving changes) and saves a snapshot in the database. The page builds the cards from the newest snapshot when it loads (`roadmap-apply.js`). Nothing to commit or push, and the Roadmap tab shows when the sheet was last pulled.
- **What comes from the sheet, per card:** title (Project Name), team, site pill (Brand), goal (the Pillar, without its emoji; the goal filter lists whatever Pillars the sheet has), status (Current Phase and Status), launch date (`eta`: Est. Launch Date, else Phase End ETA), Jira link, Estimated ROI (as the impact), and the PM. The snapshot also keeps OKR, the Goal text and the three phase dates for later use. Cards have no emoji.
- **Team mapping** (`TEAM_KEYS` in `api/_roadmap/transform.js`): Core = Core; Content & Search = Search & Content; Customer = Customer; Customer (Tiger) = Tiger team; PLC = Purchase Lifecycle; DE = Data Engineering; Dashery; Artist and App = Artist and Apps; Infra = Infrastructure; MarTech. **Contractors, a blank Team and any other value are hidden until a team is set on the sheet** (listed in `window.__roadmapHidden` and in the dry run).
- **Brand mapping** (`SITE_KEYS`): RBO, TPO, RBO + TPO and Dashery are the four pills. "Articore (All Brands)" and "RBO + TPO + Dashery" show as Both sites for now.
- **Status mapping** (sheet Current Phase, then Status, to the card; the exact table is in `api/_roadmap/transform.js`): Paused, Blocked and Delayed in Status win; then **Shipped or Done in Status = Live**; then the phase: Not Started = Not started; Discovery/Spec = Discovery; TDD/Scoping = Scoping; Ready for Dev = Ready for dev; In Dev, Code review and Ready to ship = In dev; **Dev Done = In QA**; **Impact Analysis and Complete = Live**; Deprioritized = Paused. A row with no usable phase or status shows **Not Set** (Matt Swope, Nov 10). Text dates such as "By CF" or "HOLD" show as written, and a date in another year keeps its year ("Mar 31, 2027").
- **Jira links:** a card's Jira link comes only from the Jira column of its sheet row. A row with no link shows no Jira link, and the card says "No Jira ticket is linked on the sheet row yet. Reach out to the PM." Never look up one in Jira.
- **No matching:** there is no matching by title or Jira key, no `HIDE_TITLES` and no `DROP_UNMATCHED`. The old board is only used for text: where a card's sheet name equals an old card's `sheet:` (or its title) exactly, the old description (`d`), `why` and `tags` are kept, and so is the Jira progress (`pts`) while the sheet row points at the same epic. Everything else on a new card is empty until someone writes it. Old cards with no sheet row are dropped from the team lists (the org leaderboard, `COMING.board`, and the other lists in the data file are untouched).
- **The pop-up's "Where this comes from":** for a card on the sheet, the Status, Launch date and Why it's on the roadmap lines say Roadmap sheet, Active Work tab, with the pull date. The page writes them at load from the snapshot, so do not edit them in `data/sources.js`.
- **On a refresh:** do not read Slack or Jira for the roadmap, and do not research or hand-edit `eta`, `s`, `link`, `site` or `obj` for projects on the sheet. Do not add, remove or retitle roadmap cards in `COMING.teams`: the sheet does that. Descriptions (`d`) and `why` on existing cards may be edited by hand. Leave `LATEST`, `UPD`, `DATES`, `BURN` and the other datasets that came from Slack or Jira as last written until Jay says what replaces them. If something is wrong, fix it on the sheet.
- **Changing a card:** a Product Manager asks WALL-E in Slack, or edits the sheet. The page follows at the next pull.
- **Check it:** while signed in, open `/api/roadmap-check` (can the page read the tab, and are all the columns found) and `/api/roadmap-refresh` (a dry run: filled rows, cards on the page, rows hidden until a team is set, rows with no status or Jira, duplicate names, counts by team and status). In the browser console, `window.__roadmapBuilt` gives the counts, `window.__roadmapDiff` lists the cards added, removed and changed against the data file's board, `window.__roadmapHidden` the rows kept off the page, and `window.__roadmapNoJira` the cards whose sheet row has no Jira link.
- **If it looks wrong:** ask Jay or Tom to switch `APPLY` off in `roadmap-apply.js`. The page then shows the values in the file again. A snapshot saved before this change (the old format) is ignored by the page, so the data file's board shows until the first new pull is saved.

## Automatic refreshes
One scheduled task refreshes the whole board once a day at 8:00 AM ET (Mike, Nov 3). The 2:30 PM and 4:30 PM runs and the Tuesday pre-review run are retired. Each run checks every source except the Roadmap tab and the automatically refreshed CVR numbers, runs `npm run check`, and **commits to `master` locally. It never pushes.** You get a notification; open GitHub Desktop and click **Push origin**. A run starts by fetching and rebasing onto the latest `master` (see "Branch rules"). It stops without committing if you have uncommitted changes in this folder (it will not touch your work) or if the rebase hits a conflict (it aborts the rebase and tells you which files conflict). The computer has to be awake and the Claude app open for a run to happen. If GitHub Desktop shows nothing to push, the run did not commit: look at the Refresh log in `work/projects/cvr-pacer.md` in the AI Mike folder.

The Roadmap tab (status, launch dates and Jira links) is not part of that task. It is pulled from the sheet on Vercel, so it updates even when the computer is off and there is nothing to push.

The CVR numbers (`D`, `L`, `MAX`, `STD`, `R`, `ORD`) are not part of that task either (see "The CVR numbers come from Amplitude automatically"). They are pulled from Amplitude on Vercel at about 8:30 AM ET and whenever someone clicks Refresh data, so they update even when the computer is off. The 8:00 AM task still refreshes `PROD`, `AP`, `HOURLY` and the rest, and extends `PROD` to the last complete day.

## Branch rules (read before committing)
- Always work on `master`. Before any commit, run `git branch --show-current` and confirm it prints `master`. If it doesn't, stop and tell the user.

  1. **Once per clone,** run `git config pull.rebase true`, so a pull never creates a merge commit.
  2. **Before changing anything,** run `git fetch origin`, then `git pull --rebase origin master`. Never run a plain `git pull`, `git pull origin master` without `--rebase`, or `git merge`.
  3. **If there are uncommitted changes in the folder, stop and tell the user.** Do not stash, `--autostash`, reset or discard anything: the user's work is never touched.
  4. **Right before committing,** run `git fetch origin` and `git rev-list --left-right --count origin/master...HEAD`. The first number must be `0` (nothing new on `master`). If it is not, run `git pull --rebase origin master` and run `npm run check` again, because someone else's change has landed. Do the same again before any push the user asks for.
  5. **If the rebase stops on a conflict,** run `git rebase --abort`, change nothing else, and tell the user which files conflict. Do not resolve it by deleting files, taking one side wholesale, or re-making the change by hand.
  6. **No merge commits on `master`.** Never create a commit whose message starts with "Merge branch".
- Never check out, commit to, merge, or push to the `okta-auth` branch.
- Never force-push, and never rewrite history that is already on `origin` (no `--amend` or rebase on pushed commits, no `reset --hard` to an older commit). Rebasing your own commits that have not been pushed yet, as in step 2 and 4, is fine.
